# PRD 09. 관리자·전체 흐름 추적·분석·운영

작성일: 2026-11-16 · 상태: 구현 전 설계 · 요구사항 접두어: `OPS`

[전체 설계](../main.md) · [신원·학교 권한](07_identity_school_management.md) · [공통 아키텍처](08_platform_architecture.md) · [출시 검증](10_homework_integration_release.md)

## 1. 목적

학교·교사·학생을 안전하게 관리하고, 수업과 시스템의 주요 흐름을 한 대시보드에서 추적한다. 관리자는 “어느 학교의 어떤 판본과 작업에서 누가 무엇을 승인했고 어디서 실패했는가”를 확인할 수 있어야 한다. 교사는 자신의 학급에서 다음 수업에 필요한 정보만 빠르게 본다.

사용자가 요청한 전체 데이터 로그 추적은 주요 업무 사건의 누락 없는 연결을 뜻한다. 학생의 모든 키 입력·원고·음성·대화를 운영 로그에 복제하는 설계로 해석하지 않는다. 원문을 보아야 할 업무는 별도의 권한 있는 원문 화면에서 처리하고 접근 자체를 감사한다.

운영 기반은 reading 전용 Firebase Auth·Cloud Firestore·Cloud Storage 설계다. 제공받은 Firebase 웹 설정·서버 자격은 로컬 비밀 파일에 보관했지만 프로젝트 독립성·플랜·리전·기존 데이터는 미검증이며 원격 연결은 비활성이다. 현재 관리자 화면의 역할·지표·로그·승인 상태는 합성 데이터 시연이고 실제 Firebase/IAM 권한이나 청구 내역이 아니다. `FIREBASE_CONNECTION_ENABLED=false`, `FIREBASE_ANALYTICS_ENABLED=false`를 유지한다.

## 2. 관리자 범위

| 역할 | 기본 접근 | 기본적으로 허용하지 않는 일 |
|---|---|---|
| 플랫폼 운영 관리자 | 학교 운영 상태, 집계 지표, 장애·비용·권리·감사 | 학생 원문 일괄 열람, 관리자가 스스로 학생을 가장한 제출 |
| 학교 관리자 | 자기 학교의 학급·교사·학생·소속·정책·집계 | 다른 학교 데이터·전역 키·플랫폼 요금 변경 |
| 담당 교사 | 자기 담당 학급·배정 작품·학생 질문·협업·관찰 | 다른 교사의 비공개 학급·임의 역할 승격 |
| 콘텐츠 검수자 | 배정된 카탈로그·원고·권리·판본 검토 | 학교 전체 명부·가정 정보·결제 정보 |
| 지원 담당자 | 목적과 기간이 있는 지원 티켓에 필요한 최소 범위 | 상시 전 학교 원문 검색·비밀키·무제한 내려받기 |

플랫폼 전체 역할과 학교 소속 역할은 별도 관리한다. 플랫폼 관리 기능도 서버 인가를 거친다. 긴급 접근은 사유·대상·기간·승인자·작업 이력을 남기고 종료 시 회수한다. 지원 편의를 이유로 공통 관리자 계정·학생 비밀번호 수집·학생 세션 복사를 제공하지 않는다.

앱의 `platform_admin`은 Google Cloud/Firebase 콘솔 Owner·IAM 관리자와 다르다. 브라우저 역할값이나 Auth custom claim만으로 비용 설정·규칙 변경·서비스 계정 발급 권한을 부여하지 않는다. Admin SDK를 사용하는 서버는 Firestore Security Rules를 우회하므로 모든 관리 요청에서 최신 학교/지원 범위와 자원 권한을 직접 확인한다. 일반 운영자는 서비스 계정 비밀을 보거나 다운로드할 수 없다. [Firestore 서버 접근](https://firebase.google.com/docs/firestore/security/get-started)

## 4. 학교·교사·학생 관리 흐름

1. **학교 등록:** 학교를 식별할 최소 정보와 운영 책임자를 확인한다. 이메일 도메인만으로 전 교직원 권한을 부여하지 않는다.
2. **교사 초대:** 역할·학교·담당 학급·만료일이 정해진 초대를 발행한다. 로그인한 Google 계정과 승인 소속을 연결한다.
3. **학생 등록:** 실명 수집 필요 여부부터 확인한다. 별칭/학급 번호 등 최소 식별자를 기본으로 하되 학교 내부 원본 식별자와 매핑을 분리한다.
4. **CSV 사전 점검:** 형식·중복·학교/학급 범위·예상 변경·오류 행을 보여 주고 확정한 행만 저장한다. 업로드만으로 계정 생성·메일 전송·역할 승격하지 않는다.
5. **기기 접근:** 학생별 개별 참여 티켓을 배부하고 분실 시 그 학생 티켓만 회수·재발급한다. 교사 공용 계정으로 학급 전체를 접속시키지 않는다.
6. **학기 전환:** 기존 학급을 마감하고 새 학급의 소속을 구성한다. 전년도 원문을 새 구성원에게 자동 공개하지 않는다.
7. **이동·탈퇴:** 접근 회수→자료/동의/공동작품 검토→보존·사본 이동·삭제를 처리한다. 이름이 같다는 이유로 기록을 병합하지 않는다.

중복 병합·관리자 변경·대량 내보내기·공개·삭제는 영향 범위와 대상 수를 보여 준다. 잘못된 명부 가져오기는 원본 업로드 전체를 다시 쓰는 대신 변경 집합을 취소·정정할 수 있게 설계한다. 이미 생성된 학생 활동은 조용히 다른 학생에게 재귀속하지 않는다.

## 5. 로그를 네 종류로 분리

| 종류 | 목적 | 저장 내용 | 저장하지 않는 내용 |
|---|---|---|---|
| 업무 이벤트 | 수업·책·작업의 상태 연결 | 자원 ID, revision, 행동, 결과, 도움 출처 유형 | 질문·원고 전체, 음성 원본, 가족 사정 |
| 감사 로그 | 권한·승인·공개·삭제·민감 조회 책임 | 행위자, 대상, 사유, 허용된 변경 전후 값, 승인자 | 티켓 평문·세션·비밀키·불필요한 전체 레코드 |
| 오류·성능 | 실패 원인·복구·운영 품질 | 안전한 오류 코드, 지연, 단계, 공급자 요청 참조 | 요청 body 전체, 인증 header, 학생 이름 포함 stack context |
| 비용 원장 | 승인·예산·예약·실제 사용 대조 | provider/model, 단위, 수량, 통화, 추정/청구 상태 | 결제카드 원문·학생 원고·공급자 키 |

학생의 질문 원문과 교사의 관찰 메모는 별도 Firestore 업무 컬렉션에서 필요한 기간만 보관한다. 운영 분석에는 원문이 아닌 허용된 코드와 참조 ID를 사용한다. 단순히 이름을 해시 처리했다고 익명 데이터로 단정하지 않는다. Firebase Analytics·Crashlytics·외부 관측 SDK를 설정 파일의 존재만으로 초기화하지 않는다. 아동 데이터의 목적·수집 항목·보관·국외 이전·제공자 조건과 비용을 검토한 뒤 별도 활성화한다.

### 5.1 공통 이벤트 봉투

```json
{
  "event_id": "uuid",
  "schema_version": 1,
  "event_type": "question.revised",
  "occurred_at": "2026-11-16T00:00:00Z",
  "received_at": "2026-11-16T00:00:01Z",
  "school_id": "uuid",
  "class_id": "uuid-or-null",
  "actor_profile_id": "uuid-or-null",
  "actor_role": "student",
  "resource_type": "student_question",
  "resource_id": "uuid",
  "revision_id": "uuid-or-null",
  "request_id": "opaque-id",
  "trace_id": "opaque-id",
  "outcome": "success",
  "source": "web",
  "metadata_allowlist": {"help_source": "peer", "change_kind": "clarified"}
}
```

`source`는 `web`, `paper`, `teacher_import` 등을 구별한다. `paper` 사건을 교사가 기록했다면 행위자는 교사이며 학생이 실제로 접속했다고 기록하지 않는다. 시스템 작업은 행위자 null과 시스템 주체 참조를 사용한다. `metadata_allowlist`는 이벤트별 고정 허용 스키마이고 임의 JSON 원문 적재 필드가 아니다.

활동이 여정에 연결된 경우 `activity_id`, `journey_id`, `activity_binding_id`를 선택 참조로 기록한다. 단독 사용은 여정 ID가 없어도 정상 사건이다. `journey.activity_linked/unlinked`, `journey.plan_revised`, `activity.launched/resumed`를 구분하고, 메뉴/지도 방문을 학생 수행 완료로 기록하지 않는다. 한 자원이 여러 여정에 연결되어도 읽기·질문·기여 원본 사건을 복제 집계하지 않는다. 수업별 수행 판단만 해당 binding을 기준으로 구분한다.

학교에 속하지 않는 플랫폼 사건은 명시적인 platform scope를 사용한다. 학교 ID가 빠졌다는 이유로 전체 관리자에게 학생 사건을 공개하지 않는다. 클라이언트가 보낸 역할·학교·성공 상태는 서버에서 검증/부여한다. 클라이언트 재생·탐색 telemetry는 조작·누락 가능성이 있는 관측으로 표시한다.

### 5.3 누락·위변조·조회 통제

중요한 Firestore 문서 변경과 감사/event outbox 문서는 같은 Firestore 트랜잭션에 넣는다. 트랜잭션 함수는 경합 때 재실행될 수 있으므로 안에서 AI 호출·이메일·Auth 사용자 생성·Storage 변경 같은 외부 부작용을 실행하지 않는다. 분석 전송은 커밋된 outbox로 처리하고 event ID의 결정적 문서 키와 상태 전이로 중복을 막는다. 중요한 승인·권한 변경은 감사 저장 실패 시 함께 실패한다. Auth·Storage·외부 공급자 작업은 원자적 DB 변경으로 가장하지 않고 준비/실행/확인/보상 단계와 재시도 이력을 둔다. [Firestore 트랜잭션](https://firebase.google.com/docs/firestore/manage-data/transactions)

일반 사용자와 일반 운영 화면은 감사 문서를 수정·삭제할 수 없다. 감사/outbox/권한/비용 원장 컬렉션은 클라이언트 Rules에서 직접 쓰기를 거부하며 서버 전용 경로로 기록한다. 보존 기한 삭제는 별도 서비스 권한으로 실행하고 삭제 작업도 기록한다. 프로젝트 IAM 최고 권한까지 포함한 절대적 불변 저장을 달성했다고 주장하지 않는다. 더 높은 감사 보장이 필요하면 별도 보존 저장소의 비용·조건을 검토한다.

조회는 서버에서 학교 범위를 고정하고 허용 필드만 반환한다. 여기에 이벤트 유형·자원별 행 권한을 추가한다. 학교 관리자는 조직·권한·공개 등 운영 감사에 접근하되 학생별 읽기·질문 사건은 집계 투영으로만 본다. 담당 교사는 담당 학급의 교육 목적 범위, 플랫폼/지원 담당자는 승인된 사건 조사 범위만 접근한다. actor/resource ID와 시각만으로 개별 학생 활동을 우회 추적할 수 있는 원시 이벤트 목록을 학교 관리자에게 제공하지 않는다.

이 규칙은 trace ID 검색·CSV·페이지네이션·검색 결과 수·통계뿐 아니라 Firestore 컬렉션/문서 직접 접근과 서버 API에도 적용한다. 클라이언트의 임의 이벤트 생성/수정을 차단하고 허용된 telemetry 수집 경로에서만 서버 검증 후 기록한다. 로그 조회·내보내기 자체를 감사하며 대량 조회를 제한한다. Firestore Rules는 목록을 사후 필터링하지 않으므로 직접 조회를 허용하는 예외에는 일치하는 학교/자원 쿼리 조건이 필요하다. [쿼리 보안](https://firebase.google.com/docs/firestore/security/rules-query)

## 6. 교사·학교·플랫폼 대시보드 지표

| 지표 | 정의와 계산 | 해석 한계 |
|---|---|---|
| 활성 학교/학급 | 선택 기간에 실제 수업/저작 행동이 있는 학교/학급 | 계정 생성이나 로그인만으로 수업 활성으로 세지 않음 |
| 참여 경로 | 배정 대상 중 웹·종이·교사 주도·듣기 참여가 확인된 수 | 중복 참여 가능; 미기록은 미참여와 다름 |
| 읽기 진행 | 자기보고·위치·교사 관찰을 각각 표시 | 스크롤/재생 완료를 독해력·완독 확증으로 쓰지 않음 |
| 질문 참여 | 질문을 남긴 학생/관찰 가능한 대상, 미기록 수 함께 표시 | 질문 개수로 우열·능력 순위를 만들지 않음 |
| 질문의 자립성 | 최초 시도→도움 사용→새 글의 독립 시도를 교사 루브릭으로 관찰 | 클릭 수·AI 사용량만으로 자동 점수화하지 않음 |
| 탐구의 깊이 | 근거 연결·수정 이유·다른 해석 고려의 표본 관찰 | AI 분류는 검토용 제안, 확정 성적이 아님 |
| 협업 참여 | 구상·글·그림·말하기·피드백·수정 역할별 흔적과 학생 성찰 | 글자 수/편집 횟수만으로 기여율을 산정하지 않음 |
| 교사 운영시간 | 선정+준비+검수+배부+문제 대응+평가+정리의 총시간 | 배경 탭 체류시간은 노동시간으로 계산하지 않음 |
| 생성 품질 | 검수 통과율, 부분 재생성·수정시간, 사실/삽화 오류 | 이미지 장수·완료 속도만으로 품질을 판단하지 않음 |
| 운영 안정성 | 작업 성공률·재시도·중복 방지·권한 실패·복구시간 | 분모·기간·미완료 작업·고의 공격 테스트 제외 여부 명시 |
| 비용 | 승인 한도, 예약, 공급자 사용량, 확정 청구/미확정 추정 | 미수집 비용을 0원으로 표시하지 않음 |

학생별 화면은 다음 도움을 결정하기 위한 관찰과 작업 상태를 보여 준다. 학교 간 성적 순위, 질문 수 경쟁, 읽기속도 리더보드, 자동 능력 낙인을 기본 기능에 넣지 않는다. 소규모 집계는 재식별 가능성이 있으므로 플랫폼 비교 화면에서 숨기거나 더 큰 집단으로 합친다.

교사의 시간은 표본 단원의 간단한 시작/종료 기록과 회고로 측정한다. 모든 활동마다 별도 타이머를 누르게 하거나 모든 종이 결과를 다시 입력하게 만들어 측정 자체가 일이 되지 않도록 한다.

## 7. 과금 승인과 운영 예산

사용자의 상시 지침이 최상위 경계다. **추가 과금이 발생하거나 활성화·증가할 수 있는 행동은 명시적인 사전 승인 없이는 실행하지 않는다.** 무료 한도·계정 상태·과금 여부를 확인할 수 없으면 해당 행동을 멈추고 독립적인 문서·모의 개발을 진행한다.

승인 화면/기록에는 다음이 필요하다.

- 공급자·서비스·계정/프로젝트, 목적과 데이터 전송 범위.
- 과금 단위: 토큰·이미지·음성 시간·저장량·전송량·실행시간·좌석·고정 구독 등 실제 기준.
- 예상 사용량과 예상 비용 또는 불확실성, 통화·세금 등 계산 가정.
- 승인 총액·기간·적용 작업·재시도와 fallback의 허용 여부.
- 무료 한도·잔여량의 확인 시점, 초과 요금·자동 증액·자동 갱신·취소 조건.
- 승인 주체와 명시적 결정, 철회·만료 시 처리.

현재 제공 프로젝트의 실제 요금·무료 잔여량을 검증하거나 유료 실행을 승인받지 않았다. Firebase 선택과 설정 수령은 프로비저닝·실제 연결·무료 운영 보장이 아니다. 학교 관리자라는 역할도 비용 승인 권한을 자동으로 부여하지 않는다. 개발자가 테스트라고 실행한 생성 요청·DB 조회·파일 업로드도 같은 통제를 따른다.

작업 전 예산 예약→단계 실행→실사용 대조→예약 해제/정산으로 처리한다. 승인 범위를 넘는 재생성·더 비싼 모델 전환·자동 업그레이드·기간 연장은 다시 승인받는다. 거절·만료·비용 불명확 상태에서는 새 요청을 차단한다. 소비자 서비스의 “무료 이용”을 제품 API의 무료 재판매 권한으로 해석하지 않는다.

관리 화면에는 앱 차원의 요청 상한과 제공자 청구 상한을 구분한다. 공급자가 강제 지출 상한을 제공하지 않으면 그 한계를 설명하고 초과가 가능한 구성을 임의로 활성화하지 않는다. 저장된 파일·구독·대역폭 등은 작업을 멈춰도 비용이 계속될 수 있어 종료·삭제·해지 조건까지 기록한다.

## 8. 보존·삭제·공개 회수

아래 기간은 **파일럿을 위한 제안 기본값이며 법정 보존기간을 주장하는 값이 아니다.** 실제 학교의 처리 근거·위탁 계약·보안 정책·이용 목적에 맞춰 확정하고, 학생·보호자에게 해당되는 내용을 안내한다. 미확정이면 실제 아동 데이터 수집을 개시하지 않는다.

| 데이터 | 제안 기본값 | 종료 처리 |
|---|---|---|
| 상세 운영 오류/성능 | 30일 | 식별 가능한 상세 로그 삭제, 필요한 비식별 집계만 유지 |
| 학습 제품 이벤트 | 90일 | 목적 있는 최소 집계로 변환, 재식별 위험 검토 후 최대 12개월 검토 |
| 권한·동의·발행·민감 조회 감사 | 1년 검토 주기 | 법적·계약적 필요 기간 확정 후 삭제/최소 증빙 보존 |
| 학생 질문·관찰·초안 | 학기 종료 후 90일 검토 | 학생/학교의 보관 목적에 따라 내보내기·익명화·삭제 |
| 수업 녹음 원본 | 녹음 기본 꺼짐; 사용 시 30일 | 검수·피드백 종료 후 삭제, 출판 오디오와 구별 |
| 발행된 학생 공동책 | 발행 목적·동의 기간에 따름 | 주기적 재검토, 공개 회수, 공동저작 기여/권리 개별 처리 |
| 작업 임시파일·실패 조각 | 작업 종료 후 7일 | 본 자산과 구별해 삭제; 과금/오류 최소 메타만 남김 |
| 공개 고전·검수 카탈로그 | 권리·정확성 점검 기간에 따름 | 권리 만료/분쟁 시 새 배포 중지, 판본 계보 보존 |

분석 컬렉션에서 삭제해도 Firestore 하위 컬렉션·Storage 파일·검색 인덱스·export·캐시·백업·공급자 보관본이 남을 수 있다. Auth 사용자 또는 부모 문서 삭제가 관련 자산 전체를 자동 정리한다고 가정하지 않는다. 삭제 작업은 자산과 파생본을 추적하고 결과·예외·실패 재시도를 남긴다. 보존 목적이 끝난 자료를 복구로 다시 활성화하지 않도록 삭제 표식과 복원 절차를 함께 설계한다.

이미 내려받거나 인쇄한 파일은 플랫폼에서 원격 삭제할 수 없다. 공개 링크 중지는 이후 접근을 차단하는 조치이며 과거 사본 회수를 보장하지 않는다. 이 한계를 공개 전 설명하고 불필요한 외부 공개를 기본값으로 삼지 않는다.

| AI 부적절 내용·사실 오류 | 학생 공개 중지, 원고/검토 경로로 되돌림 | 공급자/입력/판본·검수 원인 분석, 같은 자산 재사용 차단 |
| 비용 급증·청구 불명확 | 신규 과금 작업 중지·예약 동결 | 공급자 사용량과 원장 대조, 승인 없는 재실행 금지 |
| 실시간/네트워크 장애 | 마지막 확정본·저장 상태 표시 | 충돌 복구·중복 저장 확인, 종이 수업 대안 |
| homework 장애 | 연동 circuit breaker, 상태 안내 | reading 수업 지속, homework 재시도 폭주 방지 |
| DB/Storage 손상 | 승인된 복구 절차 실행 | 학교 권한·판본·삭제 표식·파일 일관성 재검증 |

백업·PITR·로그 보존·관측 서비스의 제공 여부와 비용은 플랜에 따라 확인한다. 유료 백업을 이미 활성화했다고 가정하지 않는다. 파일럿 전 승인된 백업/복구 방안과 실제 복원 연습이 필요하다. RPO/RTO 목표와 실측은 구분하고, 실제 운영 요구·예산 없이 수치를 보장하지 않는다.

## 10. 요구사항과 수용 기준

| ID | 필수 요구사항 | 수용 기준 |
|---|---|---|
| OPS-001 | 학교·교사·학생·학급 관리 | 등록→소속 승인→반 이동→회수→학기 마감의 상태가 연결됨 |
| OPS-002 | 관리자 역할별 범위 | 학교 A 관리자가 학교 B의 목록·통계·원문·내보내기를 조회하지 못함 |
| OPS-003 | 전체 주요 업무 흐름 추적 | 책 배정→질문→창작→검토→발행/출력 trace를 ID로 연결 |
| OPS-004 | 원문 최소 수집 | 로그 표본·자동 검사에서 원고·음성·토큰·티켓 평문 노출 없음 |
| OPS-005 | 서버 권위 이벤트 | 클라이언트가 성공·역할·학교 값을 조작해도 감사/상태가 변조되지 않음 |
| OPS-006 | 변경·감사 원자성 | 중요 변경 중 감사 저장 실패를 주입하면 변경이 확정되지 않음 |
| OPS-007 | 안전한 대량작업 | CSV 사전 검토·부분 오류·중복·철회·대상 수 확인이 가능 |
| OPS-008 | 비용 승인 통제 | 미승인·거절·만료·초과·불명확 비용에서 외부 과금 호출 없음 |
| OPS-009 | 지표 해석 가능 | 분모·기간·결측·종이 참여·추정/확정 구분을 화면에 표시 |
| OPS-010 | 학생 질문·협업 관찰 | 자동 성적 확정/공개 순위 없이 다음 지원에 필요한 근거 제공 |
| OPS-011 | 동의·권리·공개 회수 | 회수 후 신규 공유·내보내기·생성 차단, 이미 배포된 사본 한계 표시 |
| OPS-012 | 보존 정책 실행 | 대상/삭제/예외/실패를 확인하고 파생파일·복원 후 재등장까지 점검 |
| OPS-013 | 다국어·테마·접근성 | 주요 관리 작업을 한국어/영어·라이트/다크·키보드에서 완료 |
| OPS-014 | 장애와 복구 | 실패 작업 부분 복구, 큐 중복 처리, 비용 원장 대조 검증 |
| OPS-015 | 민감 접근 감사 | 지원 접근·로그 검색·내보내기·역할 승격의 사유/승인/기한 추적 |
| OPS-016 | homework 격리 | 연동 중지/reading 사고가 기존 프로젝트·인증·데이터를 변경하지 않음 |
| OPS-017 | Firebase 직접 접근과 서버 권한의 이중 검증 | Rules에서 거부한 민감 경로 및 Admin SDK API의 타 학교 접근이 각각 차단됨 |
| OPS-018 | Firebase 비용 경계의 정확한 표시 | Storage Blaze 조건·알림/서비스별 spend cap·실제 승인 범위를 구분하고 미승인 Billing 변경 없음 |
| OPS-019 | mock·운영 상태 구분 | 로컬 지표/비용/관리자 역할을 모의 상태로 표시하며 비활성 연결에서 Firebase/Analytics 원격 요청 없음 |

## 11. 구현 순서

P0에 학교·구성원 관리, 기본 권한/감사, 작업 상태, 비용 잠금, 최소 대시보드, 보존 설정을 포함한다. P1에 제작·공동저작·낭독 모듈의 이벤트와 검수 운영을 더한다. P2에 실제 사용량에 맞춘 집계 성능, 지원 업무, 승인된 연동 관측을 확장한다. “전체 대시보드”를 이유로 P0부터 학생 원문을 중앙 로그에 모으지 않는다.

이 문서의 법적 처리 근거는 [PRD 07의 현행 조문·공식 안내](07_identity_school_management.md#9-개인정보아동-권리공개-범위), 기술 권한은 [Firestore Rules와 서버 접근](https://firebase.google.com/docs/firestore/security/get-started), 파일 접근은 [Storage Rules](https://firebase.google.com/docs/storage/security)을 따른다. 보존기간·집계 방식·운영 절차는 제품 설계 제안이며 공식 문서가 이 기간을 의무화한다는 뜻이 아니다. Rules·서버 인가·요금 조건 검증은 구현 단계의 출시 조건이고 현재 완료 사실이 아니다.
